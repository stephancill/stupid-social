## Architecture & storage

### Targets & platform
- iOS-only SwiftPM app: the `NoFeedSocialMac` target and `.macOS` platform were removed from `Package.swift`; `@main NoFeedSocialApp` is the single entry point; no `os(macOS)`/`NS*` branches. `targetEnvironment(simulator)` `#else` branches in `SettingsView`/`KeychainCredentialStore` are intentional. Bare host `swift build`/`swift test` target macOS and don't build; verify with `stupid-app build`
- Reusable code lives in `NoFeedSocialCore` so unit tests link without the app's `@main`. Bundle id `tech.stupid.StupidSocial`
- iOS minimum `.v18`. `Info.plist`: `UIDesignRequiresCompatibility=false`; `UIDeviceFamily` `[1, 2]` (with `[1]` iPad runs phone-boxed and always `.compact`)
- Network badge PNGs live in `Resources/` (made with ImageMagick) and are listed explicitly under `resources:` in `stupid-app.yml`, because standalone imagesets weren't copied into the bundle

### Composition & protocols
- `AppContainer` (app layer) is the composition root for stores, clients, sources, `FeedService`, `FeedViewModel`, `SettingsViewModel`; `ContentView` owns only the container, loads the cached feed during setup and starts the initial story-bar fetch once the container exists. Cleanup history/justification: `docs/ARCHITECTURE_REFACTOR_PLAN.md`
- `NotificationSource.swift` defines capability protocols (notification fetching, account validation, profile fetching, target details, stories, posting, relationship mutation, activity); `FeedService` receives capabilities directly. No source-level unread counts. Rule: capability methods must be protocol requirements, not only protocol-extension helpers, or calls through an existential hit the default implementation
- Source protocols inherit `Sendable` from `SocialSource`; `DebugNotificationSource` is `@MainActor` so fetchers can be captured in task groups
- `StoryBarViewModel` owns story bar state/actions, Instagram story ordering/pagination/optimistic updates, Spotify activity fetch/seen marking and story viewer helpers; `FeedViewModel` owns only notification feed state, refresh flags, feed errors, health check and `FeedService` access
- Single home screen: `ContentView` owns the root `NavigationStack` (path `[HomeDestination]`) with the feed as root; Search and Settings are pushed via `.navigationDestination(for:)` and have no internal `NavigationStack` or Done buttons

### Accounts (multi-account)
- Any number of accounts per network. `Account` (`Models/Account.swift`): stable `id`, `network`, `remoteId` (the network's own user id: X rest id, Instagram pk, Bluesky DID, Farcaster fid, GitHub/Spotify username, Telegram user id, Apron user id), `handle`, `displayName`, `avatarURL`, Apron `serverURL`, `addedAt`, and `AccountPreferences` (category sets, where `nil` means every category so new ones start on; Instagram stories/DM shares; Apron requested name).
- Ids: new accounts get `<network>-<uuid>`; Apron's is `apron.<server URL>`, which was already its token's Keychain item. Accounts from before multi-account support keep the network's name (`x`, `instagram`…), which is the Keychain item their credentials were already in, so migration moves no credentials.
- `AccountStore` syncs the list through iCloud KVS (`com.stupid.accounts`), generalized from the old `ApronServerSync`: one entry per account id holding the account, a removed flag and when it last changed; removals stay as tombstones; the newer change wins per account. Loopback Apron servers stay on the device. Validation status (`accounts.statuses`) and what an Apron server reported at sign-in (`accounts.apronInfo`) are per device. The Debug server is a device setting (`account.debug`), not an account. Posts `didChangeNotification` (list/record changes, here or remote) and `statusDidChangeNotification`.
- Same identity twice: adding an account whose `(network, remoteId)` is already listed updates that account and moves the new credentials to it. Two devices that each added the same account before syncing both keep their entries; `accounts` lists the older and hides the newer (not for Apron, whose user ids are per server).
- `AccountMetadataStore` is now one account's view in the old per-network shapes (`xAccount`, `instagramAccount`…), so sources kept their code: reads come from the account and its status, writes update handle/avatar/preferences and the status; writing `nil` does nothing.
- `KeychainCredentialStore.scoped(to:)` keys an account's credentials by its id (X Chat keys under `xchat.<id>`, Telegram's device-local session under the id). `deleteAccountCredentials()` deletes both. The unscoped store reads the pre-multi-account items, for migration only.
- `AccountMigration` runs once per device (`accounts.migratedLegacy`): each legacy `account.<network>` metadata or Keychain credential becomes an account with the network's name as id, with fixed `addedAt` dates so every device migrates to identical entries; X Chat keys move from `xchat` to `xchat.x`; the X "follows" category is turned on once as before; a signed-in Telegram session becomes an account; each `account.apron.servers` entry becomes an Apron account. Legacy keys are then deleted. Migrated X accounts have no `remoteId` until `SettingsViewModel.repairAccountIdentities()` (foreground) resolves it, along with missing Instagram avatars and Spotify usernames.
- `AccountServices` builds one `AccountComponents` per account (clients, sources, X Chat client/unlock/live feed, Telegram client/connection) and keeps them for the account's life, so Telegram sessions and sockets survive list changes; it rebuilds on `didChangeNotification` and registers every Telegram client with `TelegramFileURLProtocol`. `FeedService`, `StoryBarViewModel`, `ChatListViewModel` and `TelegramPushService` read its components on each use. `AppContainer` reloads chats and stories and starts live feeds when the account set changes.
- Chats: `ChatListViewModel` loads one `ChatListSource` per account (`AccountServices.chatListSources`, from `AccountComponents.chatListProvider`) plus one for every Apron server, concurrently (see Chats list below). `ChatSummary.scoped(to:)` sets `accountId` and prefixes `id` with it; Apron's source scopes its own rows to `apron.<server URL>` and lists with no account id, so the list leaves them as they are. A failed account keeps its previous rows. `ChatListViewModel.connections` holds each connected account's last load (label, error), shown at the top right of Chats only when a connection failed: the badge of each failing network and a red exclamation mark, whose popover lists only the failed connections with their errors, each with a reload button that reloads the list; errors no longer appear under the search bar. A provider that lists several accounts without one (Apron) reports each in `ChatListPage.accounts`, so one Apron server failing (such as with HTTP 503) shows as that server and keeps only that server's rows. A cancelled reload keeps the last status; an account that isn't connected (`notConfigured`) has none. Chat factories in `AppContainer` take the row's `accountId`. Chat lists cached before scoping fail to decode and reload.
- Adding requires the network to say who signed in (X `verifiedUser`, Instagram homepage viewer, Spotify username, GitHub username, Bluesky DID, Farcaster fid); otherwise nothing is kept and the error shows. The X and GitHub login WebViews use the persistent store (X limits logins from a non-persistent one), so they delete only the session cookies (`auth_token`/`ct0`/`twid`/`att`; `user_session`/`__Host-user_session_same_site`/`logged_in`/`dotcom_user`) before loading; otherwise a second login captured the first account's session.

### Credentials
- `KeychainCredentialStore`: production writes synchronizable (iCloud) Keychain first, falling back to non-synchronizable Keychain (deleting any existing non-synchronizable item first to avoid duplicate-item failures); plaintext `UserDefaults` fallback (extracted values only) writes only on simulator, because Keychain can return `errSecMissingEntitlement` (`-34018`) for pseudo-signed builds. Save returns `CredentialSaveResult` (`.synced`/`.localOnly`)
- Local/legacy values are promoted opportunistically; when local and cloud items coexist the newer Keychain modification date wins and stale local copies are removed. Accounts arrive on other devices through `AccountStore`'s KVS sync; an account whose credentials haven't synced yet reads as not configured until they do
- Simulator builds use local non-synchronizable Keychain: a Keychain access-group entitlement made pseudo-signed simulator apps fail to launch with `NSPOSIXErrorDomain Code=163`
- Notification caches stay local; account preferences sync with the account

### Storage
- SwiftData `CachedNotification` properties need declaration defaults so existing caches migrate (e.g. `unreadCount` defaults to `nil`)
- `StorySeenSync` mirrors Spotify (`spotifyActivitySeenTimestamps`, keyed by `spotify:user:` URI) and GitHub (`githubActivitySeenTimestamps`, keyed by `actorId`) seen dictionaries into `NSUbiquitousKeyValueStore` under `com.stupid.storyseen.spotify` / `com.stupid.storyseen.github`. Timestamps are monotonic per actor, so both sides do an element-wise `max` merge (`StorySeenSync.merged(_:_:)`) and write back to `UserDefaults` + iCloud, converging despite KVS last-writer-wins. `UserDefaults` is the fast read path; works without iCloud. Needs `com.apple.developer.ubiquity-kvstore-identifier` (`$(TeamIdentifierPrefix)$(CFBundleIdentifier)`) in `App.entitlements`; covered by `StorySeenSyncTests`
- `SpotifyActivitySeenStore` isolates the Spotify seen `UserDefaults` persistence
- `ChatSnapshotCache` (Caches/`chat-snapshots`, one JSON per chat, keys `spotify:<chatId>` / `instagram:<threadFbid>`) keeps each chat's newest 50 raw messages plus render data (Spotify profiles, track/share metadata, partner, title; Instagram people, viewer id, legacy thread id, read receipt). View models restore in `init`, save after first load and on `disconnect()`. Paging state comes only from the live load (`hasLoadedHistory`, not `loaded.isEmpty`, which a restored snapshot would defeat)
- The Apron snapshot also stores the server's media origins so cached image embeds render as images before the session is up; otherwise `media.apron.chat` uploads rendered as cards then grew, shifting the list on open
- `CachedAsyncImage` (shared `StoryImageCache`) replaces `AsyncImage` for avatars. Optional stable `cacheKey` (`instagram-avatar-<userId>`, `spotify-avatar-<userURI>`) because Instagram signs `profile_pic_url` differently between `reels_tray` calls; on URL miss it keeps the keyed image while fetching

### Models & helpers
- `AccountStatusSnapshot` has `.networkUnavailable` and `.serviceError` besides valid/invalid/not configured; `validateAccount()` sets `.invalidCredentials` on failure but keeps `.notConfigured` for never-configured accounts. `FeedViewModel.performCredentialHealthCheck()` validates every configured source at startup
- `NotificationActor.timestamp` is optional per-actor action time (Farcaster only); `NotificationTarget` has `imageURL` and an unused `album` field
- `Date.compactRelativeTime` (`NoFeedSocialCore/Date+RelativeTime.swift`): shared compact relative time (`now`, `1m`, `12h`, `1d`, `2w`, `1mo`, `1y`)
- `RefreshTiming.measure` emits an `os_signpost` interval plus duration log (subsystem `tech.stupid.StupidSocial`, category `Refresh`) around per-source fetches and cache writes in `FeedService`, story branches in `StoryBarViewModel`, Instagram tray/per-reel, Spotify buddylist/per-track

### Usage metrics
- `AppMetrics` (`NoFeedSocialCore/Services/AppMetrics.swift`) names every event and holds the app's public ingest key; `NoFeedSocialApp.init` configures it. Events: `refresh` {network, trigger `manual`/`foreground`, outcome, value ms} plus `source_error` (both from `FeedService.fetchSourcesConcurrently`; `notConfigured` and `endpointSpikeRequired` are skips, not errors), `story_source_error` (Instagram reels), `accounts` {network, value count} once per `AppContainer` init, `chat_open` (`ChatView.task`, which re-runs when a chat reappears after a pushed screen), `message_send` {network, attachment, reply, outcome} and `message_send_failed` (`ChatViewModel.sendOptimistically`; Apron commands and over-size attachments don't pass through it), `notification_open` / `notification_reply` (Apron and Telegram, `AppDelegate`), `account_connect` {network, reconnect} / `account_connect_failed` / `account_remove` (`SettingsViewModel`), `story_open` and `story_post` / `story_post_failed`
- `StupidMetrics` is vendored in `Vendor/StupidMetrics` by `scripts/vendor-stupid-metrics.sh <tag>` (the private repo, over SSH), because stupid-app builds only local sources and static-library XCFrameworks: it fails loudly on remote SwiftPM product dependencies (observed 2026-10-29, "Unsupported build input 'product dependency'")
- Settings → Privacy → Share Usage Data mirrors `StupidMetrics.isEnabled`; turning it off drops the queue and the install id
- The notification service extension doesn't report: push decrypt failures stay in `PushExtensionLog`. MetricKit diagnostics cover the app process only
- Dashboard: `https://metrics.stupidtech.net/dashboard/apps/tech.stupid.StupidSocial`

### Preview / demo mode
- App Review preview content works in release builds (no `#if DEBUG` around `DemoData`, `FeedService`/`StoryBarViewModel` demo paths, `AppContainer`, `SettingsView`); requirement in `docs/PLAN.md` § App Review Preview Access
- Reveal: tap the Settings About heading four times, then Demo Data → **Load preview content** / Unload (explicit buttons only; the dev toggle doesn't auto-load). Also launch arg `-demoData` / env `DEMO_DATA=1`. Activation persists across launches
- `DemoData` (`NoFeedSocialCore/Sources/DemoData.swift`) builds feed notifications across networks plus story-bar content with `i.pravatar.cc` / `picsum.photos` placeholders (initials offline). Demo items are in-memory and never replace the real cache or credentials; refreshes short-circuit while `DemoData.isDemoMode`; detail/profile hydration uses fixtures; story/notification mutations (likes, seen) are skipped and demo seen state isn't pushed to iCloud. ## Feed & notifications

### Refresh policy
- Automatic refresh is foreground activation only (`scenePhase == .active` → `FeedViewModel.refreshOnForegroundActivation()` → `FeedService.foregroundActivationRefresh()`), plus pull-to-refresh. No BGTaskScheduler (iOS delivery wasn't deterministic) and no periodic polling (a 15 s loop was tried and removed)
- `ContentView` calls `refreshOnForegroundActivation()` right after creating the container, because the `.active` transition can be missed before dependencies exist. Returning from Settings also triggers it
- Foreground refresh full-fetches X notifications (not count-only), accepting X's possible server-side read side effect because fresh content is preferred
- Successful notification loads clear provider-side unread state for X and Bluesky. Instagram's notifications route already issues `POST /api/v1/news/inbox/`; Instagram DM read endpoint intentionally not used (product decision). GitHub excluded; Farcaster unsupported because Hypersnap seen writes return 501 (observed 2026-09-03)
- `manualRefresh` / `foregroundActivationRefresh` fetch all `NotificationFetching` sources concurrently (task group of `@MainActor` closures); errors are per source; refresh time tracks the slowest source
- `FeedService` reads `FeedAccountSources` (one per account, plus the Debug source) on every refresh. Items are rewritten with `NotificationItem.scoped(to:)`: `accountId` becomes the app's account id and `id` gets an `<accountId>|` prefix, since two accounts on one network can see the same event and `CachedNotification.id` is unique. Sources still build items with the network's own ids (Farcaster target details read the fid from the account, not `item.accountId`)
- Cache writes (`replaceAccount` per account + `deleteExpired`) replace only accounts that refreshed successfully and returned items; failed or transiently empty accounts keep cached rows. Each write also drops items of accounts that no longer exist (`deleteAccounts(notIn:)`), which also clears items cached before accounts were scoped
- Target details, profiles, follows and post notifications go to the account the item or profile came from (`NetworkProfile.accountId`, set by `FeedService`); a profile with no account (opened from a story) uses the network's first account. Search uses each network's first account, so people appear once
- `manualRefresh` skips `SourceError.notConfigured` and `.endpointSpikeRequired` without counting them as errors. With genuine failures and no incoming items it returns the cache if non-empty, else throws ("Refresh Issue" alert)
- Story loading runs concurrently with the feed refresh (launch, foreground, pull-to-refresh), not gated on feed success
- Feed parsing must not run on the main actor: sources/clients are `@MainActor`, so parsing after a network await blocked scrolling ~1 s (GitHub For You ~364 ms twice, Instagram tray ~359 ms). `GitHubActivityParser.parseConcurrently` and `instagramHomepageTrayConcurrently` are `@concurrent` wrappers
- `.refreshable` must stay attached permanently in `FeedView`: a conditional modifier removed it when `isRefreshing` flipped, cancelling the task (`NSURLErrorDomain -999`). Overlap is guarded in `FeedViewModel.refresh()`
- Global Cmd+R: hidden `Button` with `.keyboardShortcut("r", modifiers: .command)` in `ContentView` calls `refreshFeedAndStories(container:)` (hardware keyboards only). Toolbar `ProgressView` shows for `isRefreshing || isForegroundRefreshing`, since the native spinner appears only during the pull gesture

### Feed scope
- Apron rooms and Spotify Messages chats appear only on the Chats screen: `ApronNotificationSource` and `SpotifyMessagesSource` aren't `NotificationFetching`; they build `ChatSummary`s (`ApronNotificationSource` still validates the Apron account). `FeedService` deletes cached `.apron`/`.spotify` items on start, or they'd linger for the 24-hour retention. Instagram DMs stay in the feed until Instagram has a chat screen
- `NotificationItem.unreadCount` (`CachedNotification` default `nil`) drives a blue count capsule and blue timestamp on a row

### Notification detail
- Target hydration: `fetchTargetDetails(for:)` on the source / `FeedService`, cached by network/account/target id (`cachedTargetDetails`) so revisiting doesn't reload; unsupported sources fall back to cached metadata
- `NotificationTarget` carries optional display-safe metadata: multiple image URLs, author, posted timestamp, cached like count; decoding stays compatible with old rows that only stored `imageURL`
- Detail shows network, usernames and content in a `Post` section (avatar/name header, relative time, full text, full-width images or horizontal carousel, total likes, external link); hydration shows only a compact loading indicator. People rows push `ProfileDetailView` and show relative time only when the actor has a timestamp
- When both `parentTarget` and `target` exist, one `Thread` section shows parent, a connector line, then the reply
- X reply parents come from `globalObjects.tweets` when included. Farcaster hydrates `parentTarget` separately (payload often has only parent hash/FID); parent/reply rows keep fallback shells with placeholder bars while hydrating (no spinner swap, no inline loading row, no bare-FID author placeholder)

### UI
- Feed rows: notification-type icon, actor avatar strip, inline network badge, bold usernames without `@` (avoids display-name spoofing), relative time; no unread dots. Follow rows have no preview line. Any notification with an `imageURL` shows a 48×48 thumbnail. Summary uses interpolated `Text` (concatenation deprecated on iOS 26). Grouping text: `@user and N others liked your tweet` / `reacted to your cast` / `followed you`
- Rows use state-driven navigation instead of `NavigationLink` (avoids its reserved disclosure column) and fill the width with a rectangular `contentShape` (plain button hit-tests only drawn content). Same insets as Chats via `compactListRowInsets()`
- Trailing swipe "Open Post" (`allowsFullSwipe`) via `@Environment(\.openURL)`; URLs from `NotificationTargetURL.resolve(network:target:)` (`AppModels.swift`), shared with detail: Farcaster `quilcast.com/c/<hash>`, X `x.com/i/status/<id>`, others use the target `url`; follows/URL-less targets get no action
- `networkBadgeImage(named:)` caches badge images (used to read the PNG from disk on every row body evaluation)
- Empty state: `ContentUnavailableView` with a centered borderless **Open Settings** button calling an `onOpenSettings` closure that appends Settings to the root path

### Debug source
- `DebugAccountMetadata(serverURL:)` → `DebugNotificationSource`/`DebugNotificationsClient` fetching `GET <debug-server>/notifications`
- `scripts/debug-notifications-server.js` (Bun) binds `0.0.0.0`, appends 0–5 random notifications per request, logs to `logs/debug-notifications-server.log`, persists state to `logs/debug-notifications-state.json` so IDs/timestamps aren't reissued after restarts
- `Info.plist` has `NSAllowsLocalNetworking` and `NSLocalNetworkUsageDescription` so device builds reach a LAN debug server

## Profiles, search & settings

### Search
- Profile search uses search endpoints only (no fabricated fallback profiles): Farcaster Hypersnap `GET /v2/farcaster/user/search?q=...&limit=10`, Instagram `/web/search/topsearch/`, Spotify Pathfinder `findTopResults` (`sha256Hash=755858df4daab8d212980b02a81dcf8c9a58447de318b59d07c4651a1d0450b9`) keeping only users (observed 2026-07-14)
- Native `searchable` (shared via `SearchBar.swift`; iOS 26 Liquid Glass field at the bottom), debounced `.onChange(of: viewModel.query)`; repeated identical queries aren't suppressed (allows retry); autocapitalization/autocorrection off. Network filter `Menu` stays top-right (`.primaryAction`), backed by `ProfileSearchViewModel.enabledNetworks`/`filteredResults`. Rejected: filter in `.bottomBar` with `DefaultToolbarItem(kind: .search, …)` (draws inside the search capsule), a bottom `safeAreaInset`, a home-screen search affordance, a home `searchable` that pushes `.search`
- Empty state is a fixed-height row (`.frame(minHeight: 320)`): `GeometryReader` centering animated jankily on iOS 26 and `.containerRelativeFrame(.vertical)` crashed in `UICollectionView` layout invalidation
- Result rows show the network badge beside the username

### Profile detail
- `ProfileDetailView`: avatar, display name, verified badge, @username, bio, counts, join date, website, location, "View on Network". `NetworkProfile` has `bio`, `postsCount`, `joinedAt`, `websiteURL`, `isVerified`, `isMutualFollow`, optional `location`; GitHub shows "Repositories" instead of "Posts". `FeedService.fetchProfile` takes optional `username` (X lookup is by screen name)
- Search results are partial: detail renders immediately and lazily hydrates; count rows are hidden while hydrating
- Follow/Unfollow for X and Instagram, plus an X-only bell (post notifications) independent of following (user decision: bell doesn't imply follow). `NetworkProfile.isFollowing`/`isNotifiedForPosts`; `RelationshipMutating` backs `FeedService.setFollowing`/`setPostNotifications`, wired for `.x`/`.instagram` in `AppContainer`. Buttons render only once state is known; `ProfileDetailView.shouldHydrateProfile` forces hydration for X when either is nil and Instagram when `isFollowing` is nil. Optimistic, reverts on failure

### Settings & connections
- Top-right toolbar: Search (`NavigationLink(value: .search)`) left of the Settings gear. `SettingsToolbarIcon` observes `SettingsViewModel` directly (a plain `Bool` went stale); red dot when any credential-backed connection is invalid, attached to the gear image and offset inward because the iOS 26 glass toolbar clipped it. Connection rows show a red dot too
- `ContentView` reloads `SettingsViewModel` statuses after foreground, shortcut and pull-to-refresh refreshes (`FeedView` gets an `onRefresh` closure), so a refresh-invalidated account badges without relaunch
- Settings → Accounts lists every account (network name, an 18 pt avatar beside its `@handle` or the status alone, red dot when invalid) and pushes `AccountDetailView`; "Add Account" opens a sheet listing networks with their icons (`SocialNetwork.addable`), each pushing the network's view in add mode, and the sheet closes once the account is added. Each `<Network>ConnectionView` takes `accountId`: `nil` adds, otherwise it shows that account's preferences, a "Reconnect <Network>" login at the top only while its credentials are invalid (re-adding the same identity updates it; a different identity is added as a new account), and Remove Account (centered alert; removes the account, its Keychain credentials and cached items on every device). Telegram's detail signs in or out on this device only; Apron's detail is `ApronServerDetailView`, add is `ApronAddServerView`
- Dev mode (4 taps on Settings → About header) reveals manual cookie-header paste in the add views (WebView login is primary), the Debug row and the preview/demo controls
- Per-account notification category toggles (X, Farcaster, Instagram) and Instagram stories/DM-share toggles are `AccountPreferences`, synced with the account
- Foreground `repairAccountIdentities()` fills a migrated X account's user id and missing Instagram username/avatar and Spotify username
- `Account.avatarURL` (synced) is filled after adding and by the foreground repair when missing: X profile by handle (`_normal` suffix dropped for the full image), Instagram homepage viewer, Bluesky profile, Farcaster `pfpUrl`, Spotify profile image, `https://github.com/<user>.png?size=96`, the Apron user's avatar, and for Telegram a `tgfile:` URL from `TelegramClient.ownAvatarURL()` (`users.getUsers([inputUserSelf])`, downloaded through `inputPeerPhotoFileLocation` with `inputPeerSelf`; validated with `scripts/telegram-client.py avatar --peer self`), which loads only where a client signed in to that account can download it. Without a picture the row shows the initial. Apron rows show the server host, without an avatar. Redaction hides avatars too
- No credential-storage UI: the per-connection storage row, the Settings local-only/iCloud footer and `SettingsViewModel.hasLocalOnlyCredentials` were removed (product decision; `docs/PLAN.md` dropped the sync-status requirement). Local-only fallback storage and retry are unchanged
- Telegram rows set `avatarColorKey` to the peer id, so every chat without a photo shows initials on its `ChatUserColor` (for users the same id as their bubbles). Private chats get the row's photo (passed through `telegramChatFactory`) and `avatarUserId` beside the title.
- "Redact names" redacts every Chats row title (including Telegram groups and the Archived Chats list) as "Redacted", and row avatars show the initial
- Settings → Debug lists delivered notifications (title, subtitle, body, thread, category, whether the extension rewrote it; for Telegram the payload shape — `userInfo`/`aps`/alert/`custom` keys and `loc-key`, never text), the extension's `push-extension-log.json`, the saved Telegram avatar count, and a button posting a local notification from a saved-avatar user through the extension's code. Exists because iPhone Mirroring can't open Notification Center

## Stories

### Data & loading
- `StoryBarItem` enum (`AppModels`) wraps `.instagram(InstagramStoryReel)` / `.spotify(SpotifyActivityItem)` (and GitHub, `StoryBarItem.isGitHub`) with unified `id`, `timestamp`, `isSeen`, `userAvatarURL`, `userName`, `network`; provider-specific rendering lives in bubble views and `StoryBarItem` extensions
- Story bar state (`storyBarItems`, `storyBarLoading`, `storyBarContentLoaded`, `ownInstagramStoryReel`, `loadNextStoryBarPage()`) lives in `StoryBarViewModel`; `fetchStoryBarContent` shares one in-flight task so duplicate triggers don't fan out
- Initial load fetches Instagram and Spotify together and publishes atomically; the bar (incl. own bubble) is hidden until `storyBarContentLoaded`, with a loading skeleton meanwhile. Refreshes keep the existing bar visible until both sources finish
- Transient Instagram story fetch failure preserves existing Instagram stories: `InstagramNotificationSource.fetchStoryReels()` throws on tray failure rather than returning empty. Stories cleared only when Instagram is not configured
- Ordering: hard split unseen then seen with a compact `Seen` divider; unread Close Friends reels sort before other unread. Instagram's `reels_tray` order is only weakly chronological, so the first 15 Instagram reels are merged with Spotify reverse-chronologically and the rest appended in Instagram's order (observed 2026-05-16). Spotify activity sorted by timestamp descending
- Pagination (Instagram only): `reels_tray` gives the full ordered tray; `/feed/reels_media/` fetched for 15 active, unmuted reels per page; reaching the row end loads the next 15 (observed 2026-05-13)
- Instagram tiles: duplicate users (active reel + highlight) deduped by user PK
- Several accounts: the bar merges every Instagram account's tray (each person once, from the first account whose tray lists them), every Spotify account's friend activity (deduped by user URI) and every GitHub account's activity (deduped by actor). Marking a reel seen and liking a slide go through the account whose tray listed it (`instagramSourceByOwner`). The own-story bubble and the composer use the first Instagram account; there is no account picker for posting yet
- Seen sync: `StoryBarViewModel` pushes seen state to iCloud after `markSpotifyActivityAsSeen`/`markGitHubActivityAsSeen`, observes `StorySeenSync.didChangeNotification`, re-derives via `refreshSeenState()` (`spotifySortedUnreadFirst`/`githubSortedUnreadFirst`)

### Viewer (`UnifiedStoryViewer`)
- Single viewer for all providers, presented via one identifiable `StoryViewerSelection` holding a snapshot captured at tap time; marks seen by stable id (reel id / `userURI`). Separate bool/index/snapshot state caused blank modals, and live bar re-sorts changed the shown item
- Not `TabView(.page)`: it swallowed the dismiss drag and could show untappable empty states when the selected index was nil during `fullScreenCover` lifecycle

### Protocol & endpoints
- Legacy DMs still answer (`GET /i/api/1.1/dm/inbox_initial_state.json`, `dm/conversation/<id>.json` paged with `max_id`, `dm/user_updates.json?cursor=`, `GET /i/api/2/badge_count/badge_count.json`; probes `dm-inbox`, `dm-conversation`, `dm-updates`, `dm-unread-count` in `scripts/x-web-client.py`), but conversations moved to X Chat, so the newest legacy conversation was months old (observed 2026-10-28).
-
- Juicebox recovery with the PIN (official JS SDK `juicebox-sdk` 0.3.7 under bun; the bundler build needs the wasm instantiated by hand) returns a 64-byte secret whose halves derive the registered identity and signing public keys.
- Unencrypted messages: a create event without a key version (101), with 109 true and an unknown millisecond timestamp in 104, carries the plain `MessageEntryHolder` in 100, no franking (108) and no signature; such a conversation has no key-change events at all (observed 2026-10-29, a conversation with a user without X Chat keys). `XChatClient.decrypt` reads it directly; before, it showed as "Couldn't decrypt this message." and the Chats row as "Encrypted message". `scripts/xchat-client.py key-changes <conversation>` shows a conversation's key sources and message shapes without contents

- Create-event signatures cover the unpadded base64 ciphertext, not the plaintext; create and read-marker signatures verify against canonical payloads. Franking tags match except for events carrying media hashes, which need their own decryption.
- Incoming reactions are create events: unread counts match X's `xchat_unread_count` only when counting decrypted messages (observed 2026-10-28).

It doesn't name the key version (`latest_group_title_change_message_event` carries the same ciphertext with its version at `7.4.1.5.6`), so `XChatClient` tries each key, newest first, when loading the inbox (observed 2026-10-29). ## Bluesky

### OAuth
- AT Protocol OAuth: PAR with PKCE and DPoP, DPoP-bound access/refresh tokens; tokens and the DPoP private key in the Keychain credential store, DID/handle on the account. A login started from an account's settings finishes into that account; a new one into a new id kept between start and finish.
- Client id `https://stupidtech.net/stupid-social/oauth/client-metadata.json`, redirect `net.stupidtech:/oauth/bluesky/callback`: atproto requires the private-use scheme to be the reversed FQDN of the `client_id` host.
- Metadata served by the Worker at `workers/oauth-metadata` (route `stupidtech.net/stupid-social/oauth/*`): 200 JSON without redirect for GET/HEAD, 405 other methods, 404 other paths.
- The custom PDS (`pds.stupidtech.net`, separate `cirrus-pds-config` repo) failed `invalid_client` / metadata 404 because Cloudflare Worker routes can't be targets of same-zone Worker `fetch()` (Custom Domains can). Fix: the PDS Worker has an `OAUTH_METADATA` service binding to `stupid-social-oauth-metadata` and a fetch shim routing only the client-metadata URL through it.
- Login hint discovery: handle → DID → DID document → PDS endpoint → protected-resource metadata → authorization server (not hardcoded `bsky.social`; the wrong server gave a bogus reactivation prompt).
- PAR returns the initial `use_dpop_nonce` challenge as HTTP 400, not 401 (observed 2026-07-14); `BlueskyClient` retries nonce challenges on both.
- Token requests (code exchange and refresh) retry once on `use_dpop_nonce` with the server's `DPoP-Nonce`, and keep the newest nonce as `authNonce`. bsky.social rejects a nonce within about 3 minutes (observed 2026-10-29), so before this every refresh after sign-in failed with `serviceError("OAuth token request failed")` until the user signed in again. Probe: `uv run --with cryptography python3 scripts/bluesky-web-client.py token-nonce [--auth-server URL]` (throwaway key and invalid refresh token, so no real session is touched).
- The Cirrus PDS (`pds.stupidtech.net`) sends no DPoP nonces. It rotates the refresh token on every refresh and revokes the previous access token straight away; access tokens last 1 hour, refresh tokens 90 days (`@getcirrus/oauth-provider`, observed 2026-10-29). Two refreshes with the same refresh token therefore always fail one with `invalid_grant`, e.g. two devices sharing the session through iCloud Keychain before the rotated tokens sync.
- So `BlueskyClient` refreshes once per refresh token: concurrent callers, in any client instance for the account, share one request (`RefreshCoalescer`). When a refresh is refused with `invalid_grant`, it uses the tokens in the keychain if another device or client saved newer ones since (refreshing those if they're expiring); otherwise it throws `BlueskyClientError.refreshTokenRejected`, and the feed source marks the account invalid so Settings offers to sign in again.
- A PDS 401 that isn't a nonce challenge (`use_dpop_nonce` in `WWW-Authenticate` or the JSON error) means the access token was revoked: the request retries once with newer saved tokens or a refresh. A 401 merely carrying a `DPoP-Nonce` header isn't a challenge; retrying on that alone looped forever on a revoked token.
- Errors are `BlueskyClientError` cases (`refreshTokenRejected`, `tokenRequestFailed`, `unauthorized`, `requestFailed`), so usage metrics, which send only the type and case, say which step failed.

### Identity, homepage and session validity

- Identity and the stories tray come from the authenticated homepage (`InstagramHomepage.swift`), not the Direct inbox or a standalone tray request: parse only the `PolarisViewer` module for own identity, verify its numeric ID against the selected credentials, read the named preloaded tray payload. Homepage reads bypass local HTTP caching and share an in-flight fetch. `currentUserProfile()` (setup, validation, revalidation, composer's own actor) is built from it; numeric profile-query setup gets the viewer username from homepage state.

- Error classification (validation, settings revalidation, story refresh): generic service/parse failures keep saved credentials, known identity for the same account, and notification/story preferences; only genuine auth failures, explicit logged-out payloads and mismatched identities require reconnect. Missing usernames can be repaired even when an avatar is cached.
- Auth failures throw `SourceError.notConfigured`; sources mark metadata `invalidCredentials` but keep stale credentials for checkpoint recovery. Triggers:
  - HTTP 200 login/challenge HTML from an authenticated request.
  - Expired session: `GET /` answers `302 → https://www.instagram.com/` with `Set-Cookie: sessionid=…; expires=Thu, 01-Jan-1970 …; Max-Age=-…`. With manual cookies URLSession would follow with the dead cookie until "too many redirects"; `webDataRequest`/`webTextRequest` attach a per-task `InstagramSessionExpiryRedirectGuard` that refuses such redirects, and any response expiring `sessionid` throws (observed 2026-10-25). Covered by `testInstagramDetectsExpiredSessionCookie`.
  - Checkpointed sessions still load the homepage (with `actorID`) and expire no cookie; API calls fail instead: `POST /api/v1/news/inbox/` → HTTP 400 `{"message":"checkpoint_required",…}`, `GET /api/v1/direct_v2/inbox/` → HTTP 404 logged-out page (observed 2026-10-26). `instagramBodyRequiresLogin` matches JSON `message` `checkpoint_required`/`challenge_required`/`login_required` or an `<html>` class list containing `not-logged-in`. Covered by `testInstagramDetectsLoginRequiredBodies`.

### Login WebView

- `InstagramLoginWebView` uses WKWebView's native Safari UA (not Chrome/Android UAs) and saves only once all of `sessionid`, `csrftoken`, `ds_user_id`, `mid`, `rur`, `ig_did` exist, so verification steps can finish.

- Schema caveat: rebuilt from protobuf-lite `*_FIELD_NUMBER` constants; names/numbers reliable, some nested types not. `NodeIdentifier.node_class` arrives length-delimited, not a varint enum, so decoders fall back to generic decoding (`#<n>`) when the wire type contradicts the schema.
- Send: `POST speechless/v1/submit/request` with `ClientNodeRequest{1: NodeRequest{2: MessageRequest{1: AddContribution{1: chat id, 2: ContributionPayload{1: FreeText{1: text}}}}}}`. No node id, timestamp or digest (like the Android app); `ClientNodeResponse` echoes the created `ClientNode`, inserted directly. No reply reference for text. Probe: `spotify-web-client.py chat-send`.
- Seen: `ClientNodeRequest{1: NodeRequest{3: BulkMessageRequest{2: AddHierarchyActivity{1: chat id, 2: ActivityRequest{3: ack_type USER_SEEN=1}}}}}` marks the whole chat seen (probe `chat-seen`).
- Track metadata: spclient `GET metadata/4/track/<gid>?market=from_token` with the WebPlayer bearer; gid = base62 id as 32 hex digits. Returns name, artists, album, release date, duration and cover file ids (`https://i.scdn.co/image/<file_id>`), no preview. Probe `track-metadata`.
- Share metadata for albums, episodes, playlists: public oEmbed `GET https://open.spotify.com/oembed?url=<open.spotify.com URL>` (no auth; no artist). Senders via `user-profile-view/v3/profile/<username>`. Both best-effort, cached in memory, falling back to raw username and "shared a track"-style text.
- No realtime (Spotify's push channel unavailable), so everything polls.
- Not yet called: `retrieve/hierarchy/shares`, reactions/receipts via `submit/request`, group create/rename/add/remove/leave, mute/unmute, read-receipt settings, invites, `can-message-users`, `hierarchy/delete`. Mutations need probe validation first.

## GitHub

### Session & client
- Feed: authenticated HTML `GET /conduit/for_you_feed`, ephemeral cookie-disabled session, matching fetch nonces, ETag conditional requests. `If-None-Match` often returns 200 with a new ETag for unchanged content, so don't rely on 304 (observed 2026-08-29).
- Login WebView captures the full GitHub-domain cookie set (`GitHubCredentials.additionalCookies`), resolving duplicate names (`WKHTTPCookieStore` returns same-named cookies from multiple domains; a dictionary without a resolver crashed on `tz`). `GitHubClient` replays all except per-request `_gh_sess`.
- Session model (observed 2026-09-13): `user_session` has a two-week Max-Age, but server-side it stays active while accessed within 2 weeks, so replaying it works past cookie expiry. No refresh or re-mint: `saved_user_sessions` (`<user_id>:<session_key>`, ~3 months) alone doesn't authenticate, the cookie set minus `user_session` returns 401, and GitHub never re-sends `Set-Cookie: user_session=` on reload. Keep-alive = an authenticated request at least every ~2 weeks.
- `GitHubClient.refreshedSessionCookies(from:)` parses re-issued `user_session`/`__Host-user_session_same_site` into `GitHubForYouFeedResponse.refreshedUserSession`/`refreshedSameSiteUserSession`; both sources persist them. Foreground-only keep-alive (no background task, by choice), so 2+ weeks unopened means reconnect.
- Expired session: `/conduit/for_you_feed` 302 → `/login?return_to=…`, which `URLSession` follows to 200 login HTML (zero cards, no error). `GitHubClient.isLoginRedirect(_:)` (final URL path `/login`) makes `forYouFeed` and `authenticatedUser` throw `SourceError.notConfigured`; sources `markInvalid()` and rethrow so `GitHubConnectionView` shows "Log in to GitHub". Covered by `GitHubClientTests`.
- `dotcom_user` capture is unreliable, so `GitHubClient.authenticatedUser(credentials:)` reads the login from the `https://github.com/` homepage user-menu JSON (`"userMenu":{"owner":{"login":"..."}}`); nil when logged out, `notConfigured` on 401/403. `SettingsViewModel.saveGitHubCookies` persists it when missing; `validateDiscoveredGitHubCredentials` heals username-less sessions.
- `GitHubForYouFeedLoader` (built in `AppContainer`, shared by `GitHubNotificationSource` and `GitHubActivitySource`) fetches and parses once: concurrent callers with the same credentials share the in-flight request, and a result is reused for 10 s. Each source still persists refreshed cookies. Settings connection checks call `GitHubClient` and the parser directly.
- `GitHubClient.userPage(for:)` parses `https://github.com/<username>` (`og:description`, `tab=followers`/`tab=following` spans, `homeLocation` vcard, `nofollow me` link) → `GitHubNotificationSource.fetchProfile`. `GitHubClient.repoPage(for:)` returns `GitHubRepoDescription` from OpenGraph (`ogMeta`).

### Protocol and server behavior
- Spec: PROTOCOL.md v9, cloned in ignored `third-party/apron/`.
- Demo server (`apron-cloudflare-demo/9`): capabilities `history, edit, rooms, reactions, command, activity, embed:upload, status, ext`; `auth: [token, guest]`, `signup: [token]`, `ping: 45`. Guest auth issues no token; each connection is a new `guest_NNNN` user auto-joined to `general`, read-only (`guest_posting: false`). Upload limit `ext.media.upload[mime].max_bytes` (5 MiB per image type) (observed 2026-10-25)
- Demo server limits: connections per account ("connection limit reached for this account"; free-tier Worker); typing 10/min for accounts (guests' typing isn't broadcast or limited); `ext.settings.read_cursors: false`, so no server cursors (observed 2026-10-26)
- `apron-server-cloudflare` (`handleRoomList`) free plan: `roomListRequestsPerUserMinute: 6` for `room_list` (first `filter: "joined"` listing after auth exempt; excess returns `retry_after`); 60 frames per connection per minute (observed 2026-10-26)
- Server metadata (PROTOCOL.md v9 §3.1): the `server` frame may carry `title` (plain), `description` (CommonMark) and `avatar` (same rules as user avatars, §4.8.6), and may change per connection, such as after sign-in. The demo sends `title: "Apron Demo"`, a one-line description and `avatar: https://web.apron.chat/icon-512.png` (probe `apron-web-client.py hello`) (observed 2026-10-29)

- Read cursor is `activity.read_message_id` (§4.6); servers MAY send a user's cursor after `room_list`; the Go reference server does and persists them. Server-side unread counts exist only in push payloads (§4.9.3). Guests can't use server cursors (new `user_id` per connection).

Neither has per-room wake scopes; room `mute` is the only per-room control, hence the proposed `room_wake` extension (observed 2026-10-26)
- The server pushes only after the app's connection closes; messages while the app is foreground get no push (observed 2026-10-27)
- Local Go server: refuses `--public-url` with `--email.sender log`; without a public URL upload `write_url` is `http://localhost/…` (no port). Run `logs/apron-local/aprond --public-url http://localhost:8090` without `--email.enable`, signing in with tokens (observed 2026-10-28)

### Connection and service
- `ApronConnection` (`URLSessionWebSocketTask`) waits for the `server` frame, matches replies by request `id` (registered before send, 15 s timeout), pings `{"method":"ping"}` at `server.ping`, fails pending requests on close. Multiple `observe(notifications:onClose:)` observers, removed by token.
- Refused upgrades: URLSession reports them as `NSURLErrorBadServerResponse`, so `receiveLoop` maps a failed receive whose `task.response` status isn't 101 to `ApronError.rejected(status:)`: 503/429 read "too busy … (HTTP 503). Try again later."; others "refused the connection (HTTP n)". The body isn't exposed, so the server's error text isn't shown.
- `ApronConnection.joinedRooms()` caches the last joined-rooms listing (always `members: true`, shared by chat and Chats list), coalesces concurrent requests, drops it on `room_update` (generation bump discards in-flight older listings) — needed for the `room_list` rate limit.
- `ApronService` stores servers in UserDefaults `account.apron.servers` and per-server tokens in Keychain account `apron.<url>` (iCloud-synced). Sign-in uses `token` if saved and accepted, else `guest`; any `token` returned by `auth` replaces the saved one (§3.2.1). `denied` marks the server invalid; no fallback from rejected token to guest.
- `ApronService.session(serverURL:)` returns one shared signed-in connection per server, sharing one pending sign-in, reopened on demand; users only observe it and never close it. Each sign-in saves the connection's latest `server` frame (`title`, `description`, `avatar`, `agent`, `welcome`) to `accounts.apronInfo`, and a later `server` frame on the shared connection saves again, since each one replaces the last (§3.1); `setApronInfo` posts `statusDidChangeNotification` when it changes.
- Server names: `ApronServerInfo.displayTitle(serverURL:)` / `ApronServerMetadata.displayTitle` are the `title`, or the host without one; servers are still identified only by URL (§1). The title labels the Settings row (with the server's icon when it has one), the server detail screen (whose Server row always shows the address, and an About section renders `description`), Chats row and chat subtitles, failed-connection labels, notification subtitles (`ApronPushRegistration.serverTitle`, set on registration and room-title updates) and a saved server in the Apron link sheet, which always shows the address too so a copied title can't pass for another server (§6). `closeSessions` closes on background (via `ApronLiveFeed.stop()`), server removal, or token change.
- `ApronLiveFeed` keeps the shared connection per server while the app is active and rebuilds that server's Chats rows, debounced 800 ms. A live logged `message` rebuilds only its room (`chatSummaries(in:roomIds:)`, `ChatListViewModel.updateChats`), staying within the frame budget; `room_update` and initial connect rebuild every room (`ChatListViewModel.replaceChats(where: isApronRoom(on:))`) and update push room titles. Reconnect backoff 1 s → 60 s; `denied` stops the loop.

### Chats list and unread
- `ApronNotificationSource.chatSummaries` lists every `joined` room on every server (with `members: true` for avatars), each with its latest message (preview "You: …" or "<name>: …") however old. The row title reads "<server> / <room>": `ChatSummary.titlePrefix` = server title (or host), drawn in the secondary style and matched by search; an empty room shows "No messages yet". Servers without `rooms` get their default room from history without `room_id` (§3.4); servers without `history` produce none. Short-lived reads also store server cursors sent after `room_list`.
- A room with one other member shows that person's avatar. `ApronRoom.displayTitle(users:you:)` follows apron-web: untitled top-level private room = other members' names sorted, joined ", "; "You" when nobody else; "Private room" without a member list; other rooms use title or `room_id`. Covered by `ApronModelsTests`.
- `ApronReadStore` keeps a cursor per server/room. If `ApronService.serverTracksCursors(session)` (server has `activity`, doesn't set `ext.settings.read_cursors: false`, signed in with token), server cursors are truth, captured from our own `activity` frames, cached even when moving backward. Otherwise cursors live on device and iCloud KVS (`com.stupid.apron.readcursors`), merged per room with `max`. All `user_id`s ever had on a server are remembered (`ownUserIds`) so own guest messages never count. A never-seen room starts with its cursor at its newest message (no flood). Server-as-truth path untested.
- Unread reads a 50-message page per room; `unreadCount` = messages after cursor that aren't deleted, system or own, capped at `unreadCap` 50 ("50+").

### Chat behavior (view model)
- UIKit chat (`UICollectionView` + diffable source) chosen over SwiftUI `LazyVStack` after a 1,000-message benchmark: ~half the first-frame time and CPU, ~4× less scroll hitching.
- `ApronChatAdapter` installs snapshots by greatest `log_id` (tombstone wins ties, §2.3), orders by `message_id`, pages earlier with `before = first_log_id - 1`, joins the room if not in `joined`. `/`-prefixed text is sent as `command` when supported; `//` escapes (§4.1). Messages go out as `format: markdown`; Markdown is inline-only via `AttributedString`; raw HTML never rendered.
- Replies: `send()` adds bare `reply_to: {message_id}` (§3.5.4). Unloaded reply targets are fetched alone with `history` where `after` == `before` == id (§4.3.1), in parallel (~0.2 s each), and the first load waits for them. Missing targets show "Message unavailable" (retention, e.g. Bun server keeps 1,000 records).
- `jump(to:)`: loaded target scrolls to center and flashes; otherwise history is replaced by a window `history(before: id, limit: 30)` + `history(after: id + 1, limit: 30)`. `more` applies per direction (forward `more` → `hasLaterMessages`). In a window, live new messages aren't installed (edits are) until paging forward. `jumpToLatest()` reloads the newest page.
- Unread: cursor at open places a "New Messages" divider above the first unread from someone else for the whole visit; room opens with divider at top, or at newest when nothing unread. If the first unread precedes the newest page, open on window `history(before: cursor, limit: 10)` + `history(after: cursor + 1, limit: 50)`. Messages are marked read only when fully on screen while visible and app active, plus on send; `activity.read_message_id` sent 600 ms after the cursor last moved, only when it advances. `reportVisibleRead` waits for `.connected` and runs once on connecting, so cached messages aren't marked read early.
- Opening a room from a row with unread messages uses the shared `expectUnread()` (see Chats & chat screen): a fully-read cache is held back until history publishes the new messages, so the room opens straight at the divider; after 1.5 s the cache shows anyway.
- Reconnects: the shared connection closes silently on background; state returns to connecting and the chat rejoins on `didBecomeActiveNotification`. A reconnect reads forward from the last loaded `log_id`, `more` turning into forward paging; divider/opening window apply only to a visit's first load.
- Reactions: per-user state messageId → userId → (log_id, emojis), greatest `log_id` wins; Toggling sends your complete new set with `reactions` (§4.7). Controls only when the server advertises `reactions`. `reactors(of:on:)` names reactors from kept user objects, falling back to the recorded `from` of their reaction set (§3.3.1). Write path not verified live.
- Ownership ("includes you" for reactions, `isOwn` for messages) uses every identity the user has had on the server (`ApronReadStore.ownUserIds` + `you`), so it's right from the first cached frame; toggling still sends the current identity's set.
- Typing (§4.6), following apron-web (`sendTyping`/`composerInput`): announce `typing: 15`, refresh at most every 12 s, `typing: 0` after a 5 s input pause; sending a message only clears local state; commands send an explicit stop; skip a stop if the indication lapses within 2 s. Budget of 7 typing frames per rolling minute per server shared across rooms; excess dropped. Incoming typing ends on expiry, `0`, or a message from that user.
- Drafts use the shared `ChatDraftStore` (see Shared chat architecture); removing a server removes drafts whose `chatKey` starts with `apron:<server>|`; replies/attachments not kept.
- Members: `ApronRoom` decodes `members` and `member_count`. Set starts from `room_list members: true` (or `room_update.joined`), then live `room_update.memberships` (§4.2.2). `member_count` not adjusted live; `members` is `nil` without `rooms`.
- Presence: `ApronUser` decodes `status` (§4.5); Live `user` (`new`) notifications merge into kept objects (§3.3.1). Own entry follows `you.status` (`invisible`/`""` → offline), since the server only sends your own setting. `ApronUser.lastSeen` returns `seen` only while `offline`; decoded, merged and cached.
- `ApronUser` has hand-written `Codable`: free-form `ext`, only `ext.bio` read; an odd value never drops the user.
- Mentions: regex `ApronMention.pattern` (core) follows Appendix A.3 (no letter/digit before `@`, so emails aren't mentions), never inside code spans; a link wins over a mention inside it. Linked by text, not only when in `body.mentions`. `mentionNames` maps `user_id` → name, omitting names shared by another known user (§3.3.1) and unknown users (keep `@user_id`); tap target is always the `user_id`.
- Sending fills `body.mentions` with known users written as `@user_id` (§3.5.5). `@` autocomplete (up to 5; prefix matches on name or `user_id` first, then name words; empty query lists online first) inserts `@user_id `.

### Message cache
- The room's snapshot (through the shared `ChatSnapshotCache`, under the server's account) holds the newest 50 messages plus user objects of authors and reactors, and reactions, device only. The framework saves it 1 s after changes while connected and on leaving; the adapter returns none while an older window is showing. Removing a server removes its snapshots and drafts. Caches from the old `Caches/apron-messages/` aren't read.

### iCloud server sync
- Each server is an account in `AccountStore` (id `apron.<server URL>`, see Accounts), which replaced `ApronServerSync` and its `com.stupid.apron.servers` key. Tokens sync via iCloud Keychain (`saveApronToken`, synchronizable, item `apron.<server URL>` = the account id), read cursors via iCloud KVS.
- `ApronService.servers` is built from the Apron accounts plus this device's sign-in info and status. On `AccountStore.didChangeNotification` it compares server sets: a server removed elsewhere drops local cursors, cache and drafts but leaves the token to Keychain sync; servers added elsewhere sign in on first use with the Keychain token if present. Changes post `serversDidChangeNotification`.
- Loopback servers (`localhost`, `127.0.0.1`, `::1`) aren't synced (they'd point at the other device).
- `apronOwnUserIds` syncs via KVS (`com.stupid.apron.ownusers`) as a per-server union, so guest messages sent from another device render as your own. Two-device sync untested.

### Apron links
- `ApronLink` parses `https://link.apron.chat/#…` and `apron:?…` (Appendix A.4, link.apron.chat `SPEC.md`): form-decoded keys (bare `+` = space), first value of a repeated key wins, unknown keys ignored; for the web form, query keys count after the fragment's. A `token` in the query is refused (link.apron.chat already received it). `server` must be `wss`, or `ws` on loopback, no user info/fragment; empty path becomes `/` to match saved servers; other transports (e.g. `webrtc`) fail naming the transport. `message` positive decimal < 2^53, requires `room`. A link without `server` is valid only in content from an Apron server (resolves against that chat's server). `webURL` writes the web form (SPEC.md §4 encoding, never a token). Covered by `ApronLinkTests`.
- Entry points: `apron` URL scheme, universal links, and taps in chat text, link cards and image embeds; `NotificationRouter.open(_:contentServer:)` is the single entry point. A link to a room already in the Chats list on a saved server opens directly; otherwise `ApronLinkView`/`ApronLinkViewModel` (punycode host, escaped hidden characters) acts only on tap (add server as guest, join room, sign in with a link token via `addServer`/`updateToken`). The app never makes email/external proposals, so every sign-in link needs confirmation.
- `ApronLinkView` is laid out like a group invite: a sheet fitted to its content (measured `.height` detent), close button, large avatar (a room's initial with the server's icon, or Apron's, as a badge), title, subtitle, the server address under them (always, so a copied title can't pass for another server), optional description and member faces, at most one note, and one prominent button. Two text sizes only: `.title2` for the title and `.subheadline` for the rest. Notes are limited to a private/missing room, a failed preview, or the trust warnings for sign-in and new servers.
- Room preview: on a saved server only, `ApronLinkViewModel.loadPreview()` lists the one room on the shared session (`ApronConnection.room(roomId:)`: `room_list` with `filter: "all"`, `members: true`, `room_id`) for title, description, member count and faces. A server the user hasn't used isn't contacted before confirming (PROTOCOL.md A.4), so its links show the link's IDs. The demo returns an unlisted room in `not_joined` with full `members` and `users`, and answers an unknown (or invisible private) room with `-32602 Unknown room`, shown as private or missing (probe `apron-web-client.py rooms --members --room-id <id>`) (observed 2026-10-29)
- `NotificationRouter` holds an opened link until the Chats list has loaded (`hasLoaded`), since that list says which rooms are joined; otherwise a cold launch offered "Join Room" for a joined room.
- Linked message: `AdapterChatViewModel.focusMessageId` runs `jump(to:)` after first load; linked member opens `ApronChatView(profileUserId:)`; a link to the open room acts in place. Focus travels as `NotificationRouter.pendingFocus` beside `pendingChat`, leaving `ChatSummary.Destination`'s cached encoding unchanged. Messages with a `message_id` have "Copy Link" (web form).

## Telegram

### Approach & constraints
- No HTTP API for user accounts, and stupid-app rejects binary targets (`Planner.swift`: "binaryTarget … unsupported"), so TDLib is out; the app implements MTProto 2.0 itself. Session is device-local (Keychain, not synchronizable, under the account id); the account itself syncs, so another device lists it and offers to sign in there. A new sign-in whose user id is already listed moves its session to that account (`TelegramClient.moveSession(to:)` then `reloadSession()`). Each account registers the APNs token with the other signed-in accounts' user ids as `other_uids`. Telegram pushes name the chat but not the receiving account, so a tap opens the first listed chat matching the peer's kind and id. `tgfile:` URLs don't name the account either: `TelegramFileURLProtocol` tries each signed-in client in turn. API id/hash are build-time from gitignored `Resources/TelegramAPI.json` (public repo); without it Settings shows "Telegram, Unavailable". Broadcast channels skipped
- TL codec is generic over the official schema (`scripts/telegram-schema.py` → `Resources/TelegramSchema.tl`, layer 225, deduplicated by constructor id). MTProto and API schemas both define `message`: encode-by-name prefers the API one, decoding goes by id
- Swift matches the probe byte for byte (`TelegramTests`: AES-IGE, 2048-bit modpow, SRP, `messages.sendMessage` encoding vectors); `testLiveHandshake` runs with `TEST_RUNNER_TELEGRAM_LIVE_TESTS=1`. A modpow takes ~1 s in debug builds; key exchange is once per device, SRP once per sign-in
- `TLSchema` is `@unchecked Sendable` (immutable; parameter tuples not inferred Sendable); transport's one-shot start flag is a class because `NWConnection` state handlers are `@Sendable`

### Connection
- DC migration: `auth.sendCode` may answer `PHONE_MIGRATE_<n>` and the client moves DC; 2FA via SRP. Cross-DC file access uses `auth.exportAuthorization`/`importAuthorization`
- Calls time out after 25 s by closing the session (a socket iOS dropped during suspension can stay silent); the client reconnects and retries
- A failed write or ping in `MTProtoSession.send` closes the session so calls fail as `connectionLost` and reconnect-and-retry runs (raw transport errors such as `NWError` 57 "Socket is not connected" after iOS suspends sockets didn't trigger reconnect)

### Dialogs & messages

## Chats & chat screen

### Shared chat architecture
- `ChatViewModel` (Core) is network-agnostic: published state and display models (`ChatMessage`, `ChatUser`, `ChatEmbed`, `ChatReaction`, `ChatReactor`, `ChatAttachment`), overridable actions, capability flags (`canReply`, `canReact`, `offersAttachments`, `mentionPattern`, `showsSenderNames`). Its only subclass is `AdapterChatViewModel`, which drives a network's `ChatAdapter`; the base's no-op actions are what an adapter without that ability gets. `ApronChatAdapter` keeps `ApronMessage` snapshots and maps to `ChatMessage` on publish (embed mapping incl. the allowed-media-origin rule lives in the adapter)
- `ChatUIKitView`/`ChatViewController` (cells/helpers named `Chat*`) take any `ChatViewModel`; cells re-render when their `ChatMessage` or group layout changes, not on `log_id`. `ChatView` = SwiftUI screen (title pill, connect/disconnect, reconnect on activation); `ApronChatView` adds members/profiles; `NetworkChatView` hosts other networks. `ChatViewModel.network` puts `NetworkBadgeIcon` before the subtitle in `ChatTitlePill`, and `titleAvatar` puts a `ChatAvatarImage` before the title: the one-to-one partner when the adapter sets `avatarUserId` (from `ChatInfo`), else the chat's own picture from its Chats row (`showRowAvatar`, called by `ChatsView.opened` with the row's `avatarURL`/`avatarColorKey`), so groups, rooms and every network show what their row shows
- `publish(history:reactions:)` sets reactions before messages, and the screen keeps totals for messages not yet shown, so first render includes reactions (separate subscriptions rendered bare bubbles that then grew). Apron applies reactions first itself; Telegram, Instagram, Spotify, X Chat use `publish`
- Adapters (`AdapterChatViewModel.swift`): `ChatAdapter` is one conversation with no UI state (info, messages, reactions, `loadNewest`/`loadEarlier`/`send`, read position, snapshot as `Data`); optional abilities are separate protocols (`ChatReactionSending`, `ChatAudioPreviewing`, `ChatLiveUpdating` for pushed updates, `ChatReferenceResolving` for quoted messages outside the loaded ones), so `canReact`, audio previews, following and quotes follow from conformance rather than a flag that could disagree with the code. `AdapterChatViewModel` (final) drives one: restores the snapshot and places the divider before the first render, connects, polls at `pollInterval`, debounces `markRead`'s returned send, and republishes when the adapter calls `onChange` (a profile or track loading later). Every network uses it (`*ChatAdapter`, next to their clients). `AdapterChatViewModel<Adapter>` is generic so a network's own screens reach their adapter typed (`ApronChatView` reads `viewModel.adapter.room`). Apron also implements `ChatWindowing` (older windows, jump, latest), `ChatTyping`, `ChatMentioning`, `ChatCommanding` (a command waits for the server instead of showing a sending copy, since it may post nothing) and `ChatLinking`; live adapters report a closed connection through `onConnectionLost` (an error shows with Reconnect; without one the app closed it and reconnects when active) and background failures, such as an upload after its message posted, through `onError`. Apron's members, profiles and notification level are `ApronRoomViewModel`, which the adapter keeps current and the members and profile screens observe. `connect()` is guarded while connecting and while open, so the `.task` and app-activation calls can't start following twice. Telegram's member list has its own `TelegramMembersViewModel` (member state is screen state, not adapter state), built by the same factory as the chat; its 30 s poll reloads the dialog with the page, which also re-reads "last seen". Spotify's "seen" now goes through the shared 600 ms read-marker delay too
- Shared behavior lives in `ChatViewModel`, and networks use it instead of their own copies (the target shape and migration status are in TECHNICAL_DESIGN.md § Chat Framework):
  - `chatKey` (`<account id>|<network>:<id>`; Apron's is `apron:<server>|<room>`, since each server is its own account) names the chat for drafts and snapshots. The account is part of it because two accounts can be in the same chat, such as a Telegram group; snapshots cached under the old unscoped keys are left unread
  - drafts: `ChatDraftStore`, `UserDefaults` `chatDrafts` by `chatKey`, for every network. It replaced Apron's `apronDrafts`, whose drafts weren't migrated
  - polling: `startPolling(every:)` / `stopPolling()` call the network's `poll()` (Spotify 10 s, Instagram 20 s, Telegram 30 s as a fallback to pushed updates); `isPolling` doubles as "already connected"
  - unread: networks override only `isAfterReadPosition(_:)`; `isUnread`, `updateUnreadCount()` and `placeUnreadDivider()` build on it. Apron overrides `updateUnreadCount()`, since it counts its kept snapshots rather than a possibly older `history` window
  - `scheduleReadMarker` sends the read position 600 ms after it last moved (Apron, Telegram, Instagram, X). Spotify marks a whole chat seen at once and doesn't debounce
  - links: `link(toMessage:)` (Copy Link), `linkTarget(for:)` (links to this chat's messages or members) and `linkBaseURL` (relative links), so `ChatUIKitView` never casts to a network's view model
- `ChatsView` calls `expectUnread()` when the row has unread: if the restored snapshot has none (`unreadCount == 0`), `messages` stays empty until `state` leaves `.connecting` or 1.5 s pass, so the chat opens once at the divider. `AdapterChatViewModel` places the divider from the restored snapshot before the first render, and drops it after loading when history replaced the message it sat on; X Chat has no snapshot and waits for history. Deleted messages never count as unread. `placeUnreadDivider()` reads `history`, not `messages`: while restored messages are held, `messages` is empty, and reading it left these chats without a divider. Covered by `ChatViewModelTests`
- `sendOptimistically` (all networks): message shows at once with a clock by its time; the network's copy replaces it; networks set `history`, not `messages`. A sending photo uses the media layout; the confirmed message keeps the picked image file and aspect ratio so only the time badge changes
- No jump on send confirmation: a pushed update can bring the sent message into history before send returns its id. `composeMessages` matches a "sending" message to a new own message with the same text not in history at send time; the view keeps the confirmed message under its "sending" item key (`sentLocalIds`, `itemKey(for:)`) so the cell is reconfigured, not replaced; a swap adding no row settles at the bottom without animation

### Chat screen behavior
- Reactions: `applyReactionTotals` reconfigures changed bubbles in one 0.3 s ease-out animation pinned to the bottom (`applyKeepingBottom(_:animated:)`); not before the initial scroll or while anchored to the unread divider. Scrolled up, reactions grow upward (lowest visible message stays put, `lowestVisibleItem()`). Other growth (quotes, mention names) applies without animation
- Changes while a context menu shows wait until its dismissal ends (`willDisplayContextMenu` / `willEndContextMenuInteraction`): the dismissal preview kept the old bubble size and cut the grown bubble
- Every configure rebuilds media, embed and reaction views; the cell lays out those stacks once without animation after rebuilding (else zero-frame views animated in from the corner inside `applyKeepingBottom`)
- Context menu: quick reactions 👍 ❤️ 😂 + More Reactions smiley icon at the end; a fifth small element wraps onto a full-width row; 🔥 is in the picker
- Tapping the message list dismisses the keyboard (`cancelsTouchesInView = false` so links/cards/images/reactions still get taps)
- Quotes (Markdown messages only; Instagram/Spotify plain text unchanged): `ChatAttributedText.formatQuotes` drops `>`, indents 12 pt, dims to 70%, tags `.chatQuote`; `ChatLinkLabel` draws a 3 pt bar per run of quoted lines as sublayers in `layoutSubviews` because UILabel on iOS 27 rarely calls `drawText(in:)`. `ChatLinkLabel.layout(in:)` is shared by bars and hit-testing and returns the `NSTextStorage` too, since `NSLayoutManager` holds storage weakly
- Cards: link/file card symbols have a fixed 22 pt frame with required compression resistance. Bubbles with previews/cards take `maxContentWidth`, `embedsStack` uses `.fill`; preview images keep aspect ratio, cropped to at most 4:3 portrait (`max(ratio, 0.75)`). Uploaded images keep Telegram-style sizes
- Reply quotes: `ChatViewController` keeps each reply's rendered quote with its rendered message/layout and reconfigures the reply when the quote changes, because a quoted message often arrives in `messages` not `referencedMessages` and the diffable data source won't reconfigure an unchanged reply ("Loading…" stuck). `replyQuote(for:)` checks the view's own `messagesById` first
- Composer `ChatComposerTextView` handles hardware Return in `pressesBegan`: sends when the send button is enabled and swallows the press end; Shift-Return adds a line; on-screen Return arrives as text; while `markedTextRange` is set, Return confirms IME composition. Not a priority `UIKeyCommand`, which would steal the IME Return
- Swipe-to-reply pan sets `allowedScrollTypesMask = .continuous` (two-finger trackpad); `.discrete` mouse wheels excluded since each notch would start and end a swipe
- Redact names (`DebugRedaction.isEnabled`, `redactionEnabled` default) covers sender names, initials, reply quotes/preview, typing names, reactors, mention suggestions, mentions in text (`@Redacted`), Apron member list and profile. Titles redacted when they name people (`!showsSenderNames` or `ChatViewModel.titleNamesPeople`), plus `@username` subtitles. Plain-text names in bodies are not redacted

### Home pager
- `ContentView`'s root is `HomePager`: `UIPageViewController` (`HomePagerController`) with two `UIHostingController`s — `NavigationStack` for `ChatsView` left, feed right. Not SwiftUI paging `ScrollView`/`TabView`: both lost hosted navigation bars' layout margins, and `scrollPosition` didn't apply initially
- Pages wrap: the data source returns the other page both before and after, so swiping on past either page lands on the other. The dots reflect the scroll position back into 0...1 past either end. They measure a swipe from the page shown when the offset was last at rest, not `viewControllers.first`: the page controller switches that while the swipe is still settling, before the offset returns to the middle, which made the dots flick back and forth after each swipe
- Paging (`isScrollEnabled`) off whenever the visible side has a pushed screen, tracked from navigation state (`ChatsView` selection, feed detail selection and path), so back swipe and swipe-to-reply aren't taken over. Not via root `onAppear`/`onDisappear` (outgoing page's `onDisappear` fires as a swipe begins)
- `updateUIViewController` calls `setViewControllers` and updates dots when the bound `page` differs from the shown page. An animated programmatic `setViewControllers` leaves cached neighbours stale, so the page is set again without animation after it finishes
- `HomePageDotsView` (UIKit) shows dots bottom centre only while paging is enabled (never over a composer), on a `.systemMaterial` pill (thin was too faint over white rows), styled like story-row dots. `HomePagerController` observes the scroll view's `contentOffset` by KVO (page controller stays its delegate) and updates the view directly; pushing offset through SwiftUI state re-rendered both roots each frame and cancelled the pan
- Last page stored in `@AppStorage("homePage")` (`HomePage` is `String`-backed), restored at launch

### Chats list
- Networks take part through `ChatListProvider` (`network`, `chatList() -> ChatListPage`): `ApronNotificationSource`, `SpotifyMessagesSource`, `InstagramClient`, `TelegramClient`, `XChatClient`, each wrapped in a `ChatListSource` with its account id and error label; `AppContainer` passes `ChatListViewModel(sources:)` a closure, read on every load since accounts come and go. Providers load concurrently in a task group and merge in source order. `ChatListPage.archived` is `nil` when the archive didn't load (Telegram's folder 1 request failed, or X's archived rows after its inbox), which keeps that network's archived rows; networks without an archive return `[]`. The protocol is `Sendable`: every provider is `@MainActor` or an actor, and the task group needs it (Swift 6 region checking rejects capturing non-Sendable providers)
- Live updates go through generic calls: `updateChats(_:)` (rows by id, X Chat's socket and Apron's per-room rebuild) and `replaceChats(where:with:)` (a set of rows, such as one Apron server's rooms via `ChatSummary.isApronRoom(on:)`)
- `ChatSummary.presence` (`ChatPresence`: online, last seen, recently, within a week or month) is the framework's presence type; Telegram fills it for one-to-one chats
- `ChatListViewModel` merges `ChatSummary`s per network (Apron: every joined room on every server regardless of age, unread via the shared read store). A failing network keeps previous rows and shows its error above the list; unconfigured networks contribute nothing; `CancellationError`/`URLError.cancelled` aren't failures (opening a chat cancels the list's `.task` reload). Reloads on appear, on return from a chat, on pull-to-refresh. Rows open via `AppContainer.spotifyChatFactory` / `telegramChatFactory` etc.
- Saved to `Caches/chat-list.json` after each load, restored when `ChatListViewModel` is created; a disconnected network loads empty and drops out. Adding a `ChatSummary` field makes old saved lists undecodable; the first load rebuilds them
- `follow(_:chatId:)` wires an opened chat to its row: `ChatViewModel` reports its newest message (skipped while an older window shows) as a one-line preview (mentions by name, "Shared “title”" for cards/tracks, "Photo" for images) and unread count; `You: ` prefix for own messages, or sender name where `ChatSummary.namesSenderInPreview` (Apron rooms, Spotify groups). The reload on return still runs
- `ChatSummary.titleNamesPeople`: Apron rooms named for members (`isNamedForMembers`), Spotify DMs, every Instagram thread (`thread_title` may be custom or members' names, indistinguishable). With redaction on, `ChatRow` uses `DebugRedaction.chatTitle`/`chatPreview`: titles "Redacted", initials follow title, photos stay; `@` mentions → `@Redacted`; in sender-named rows the part before the first ": " → "Redacted" except "You: "; in DMs the title and each of its words are redacted as whole words in previews. Search still matches real names
- A showing `navigationDestination(item:)` doesn't swap when its item changes, so `ChatsView` clears the selection and opens the new chat 450 ms later
- `ChatListViewModel.chat(for:)` turns an open request's destination into a chat: the row listed under exactly that destination, else the first `ChatListResolving` provider's answer, given only its own rows. `TelegramClient` matches on kind and id (a push has no access hash); `ApronNotificationSource` stands in for a room the list doesn't have yet (titled by its id) and a direct chat with no room yet, using the same row id builder as its list. `ChatsView` holds no network knowledge here
- Notification-tap open requests for Telegram chats are kept in `ChatsView` until a load lists the chat (opening needs the access hash from the list; not loaded yet on cold launch)
- `ChatsView` inserts rows 50 ms after appearing: rows present while the drawer search bar first lays out collapse the list to the inline title (`defaultScrollAnchor(.top, for: .initialOffset)` and first-`.task` insertion didn't help)
- Search filters by title and latest message (`localizedStandardContains`) via shared `searchBar(text:prompt:placement:)`; Search uses `.automatic`, Chats `.navigationBarDrawer(displayMode: .always)`
- Rows: separator starts at text (`.listRowSeparatorLeading`), top separator hidden on the first row only (hiding on all rows hid shared separators), network badge on an opaque system-background tile (Spotify's round badge has transparent corners). `ChatRow.timeLabel`: time today, abbreviated weekday within 6 days, `.dateTime.day().month(.defaultDigits)` earlier this year, `.numeric` before

## Push notifications

### Relay
- Why Web Push to a relay: native apps can't get a browser push subscription and the demo server lacks `relay`; registering `webpush` everywhere gives one format (RFC 8291 `aes128gcm`) and one decryption path. The relay seals device token, environment and the server's VAPID key into the endpoint id: no database, and pushes signed by another key are refused.
- `workers/push-relay` (Worker `stupid-push-relay`, `push.stupidtech.net`), APNs key `U7W6CW4B57` (team `6JKMV57Y77`). Valid-key check: a fake device token gets `BadDeviceToken` with the right key, `InvalidProviderToken` otherwise. Secrets `RELAY_SECRET` and `APNS_PRIVATE_KEY`; changing `RELAY_SECRET` invalidates every endpoint. Responses: unsigned push 403, APNs device rejection 410, refused provider token 502. Tests: `bun run push-relay:test`.
- APNs provider token cached in `caches.default` (key `https://push.stupidtech.net/internal/apns-provider-token/<key id>`, 49 minutes) as well as memory, because new isolates each signed a fresh token and APNs answered 429 `TooManyProviderTokenUpdates` (refreshes more often than every 20 minutes) (observed 2026-10-27). That URL isn't publicly served (Worker answers 404).

### App & extension
- `NoFeedSocialPush` module and `NoFeedSocialNotificationService` extension (`tech.stupid.StupidSocial.NotificationService`; an extension bundle ID must start with the app's, so it keeps `tech.stupid`). App has `aps-environment` and App Group `group.tech.stupid.StupidSocial` APNs environment comes from the embedded profile's `aps-environment` (absent in App Store/TestFlight → production).
- `ApronPushService.register` chains registrations per server so each reuses the relay URL the previous saved; concurrent runs created duplicate registrations for one `push_id` (one push each). Stale ones can be removed with probe `push-unregister`.
- Apron notification: title "<sender> in <room>" (sender alone in DMs), subtitle the server host only, no mention/reply labels; donated as one-to-one from a person named like the title (no group name/recipients) so iOS keeps that title; person identifier per sender. Plain text body with named mentions, avatar via Communication Notifications, inline Reply action (category `apron.message`). Undecryptable payloads fall back to "Apron / New message". Details in `docs/TECHNICAL_DESIGN.md` § Apron Push.
- `CommunicationNotification` (shared by extension and Debug): sets the body before `updating(from:)` and returns the updated content untouched (a mutable copy may lose the communication context). Extension Info.plist declares `NSExtensionAttributes.IntentsSupported = [INSendMessageIntent]`; app `NSUserActivityTypes` has `INSendMessageIntent`. Entitlements: communication, Siri, App Group.
- The extension logs each run to `push-extension-log.json` in the App Group (no names/text), including Telegram pushes it leaves alone. After a real push: no entry = extension didn't run (no `mutable-content`), `no avatar` = sender photo not saved, an error names the failing step.
- `AppDelegate` notification delegate methods use completion-handler forms called from a `@MainActor` task: the `nonisolated async` `userNotificationCenter(_:didReceive:)` returned off-main and UIKit aborted (SIGABRT) on cold launch from a notification.
- Replies to a notification when the app is terminated: iOS launches it in the background and a standalone `ApronService` connects; failures surface as a "Reply not sent … unknown room" notification.

### Telegram notifications
- The extension has no Telegram session, so the app writes each user avatar loaded through `tgfile:` (`avatar-user:<id>-…`) to `telegram-avatars/<id>.jpg` in the App Group (`TelegramAvatarStore`), and group photos (`avatar-chat:`/`avatar-channel:` keys) to `telegram-avatars/group-<id>.jpg` (named by id alone, since history avatar keys call supergroups `chat:` too).
- `TelegramPushChat` recognizes a Telegram push without `loc-key`: `channel_id`, `chat_id` or `from_id`, in `custom` or top level, as strings or numbers; never an Apron push.
- `TelegramPushNotification` handles private messages (`MESSAGE_*`, `from_id`) and group messages from a person (`CHAT_*`, `chat_from_id`, sender in `loc-args[0]`); channel posts and messages sent as a channel/group are left as Telegram sent them. Text messages show the text alone; other kinds keep Telegram's line, formatted from the app bundle's `Localizable.strings` (the extension has none). Also accepts `aps.alert` `title`/`body` without `loc-key`, and sets title and body itself.
- Group messages are donated as a group conversation: `INSendMessageIntent` with the group name as `speakableGroupName` (carrying the group photo), two recipients (sender plus a placeholder for the user, since iOS needs more than one for a group); the sender keeps their own photo.
- `title`/`body` group pushes: `TelegramPushNotification.senderName` is optional; the sender comes from `alert.subtitle` when present (title "<sender> in <group>"), as Telegram-iOS's `NotificationService.swift` reads title/subtitle/body. Otherwise `CommunicationNotification.telegram` shows the group as the sender (name, photo, one recipient, no group name) with the body unchanged — using the group title as sender in a group conversation showed the group twice. Covered by `TelegramTests`.
- Opening a Telegram chat removes delivered notifications naming it (matched by chat in `userInfo`, not the thread, which is Telegram's own when the extension doesn't run), and the open chat's notifications aren't presented.

### Simulator limits
- `stupid-app run --simulator` signs with only the App Group entitlement: it strips `aps-environment` (simulator refuses team-less signatures carrying it, POSIX 163), so no APNs token, and without the communication entitlement iOS ignores the intent (app icon drawn). Ad hoc re-signing with either makes the simulator refuse to launch, so avatars can only be checked on a device.
- `simctl push` doesn't run Notification Service Extensions; `stupidsim push` runs the real `.appex` for `mutable-content` payloads and prints its output. `stupidsim notification open|reply` drive banners.

### Open issues
- Whether Telegram's APNs pushes carry `mutable-content` (needed for the extension, hence any avatar) is undocumented and unconfirmed on device; avatar drawing (Telegram and Apron, including group photos) has never been seen on a device.
- iOS's communication layout may not show `subtitle`; if the Apron server host is missing on device, move the line into the body.

## Build, signing & release

### Signing & provisioning
- Adding a capability (iCloud KVS, App Groups, associated domains such as `applinks:link.apron.chat`) means enabling it on the App ID and regenerating both development and App Store profiles; a profile created before the capability doesn't authorize it (`run --network` / archive fail signing)
- Saving App ID capabilities invalidates but keeps old profiles; with the default name `signing setup` then reuses them or fails HTTP 409 on duplicate names (e.g. two `tech.stupid.StupidSocial Development`). Pass a new `--profile-name` (e.g. `"iCloud"` → `iCloud tech.stupid.StupidSocial Development`), or delete the duplicates in App Store Connect to reuse the default name
- stupid-app ≥ 0.0.23 replaces profiles that don't authorize the source entitlements; the App Store profile is now `tech.stupid.StupidSocial AppStore 2`. Development profile: `signing setup --kind development --bundle-id tech.stupid.StupidSocial --profile-name <name> --udid …`
- The notification extension needs its own distribution profile: `signing setup --kind distribution --bundle-id tech.stupid.StupidSocial.NotificationService`. `signing setup` once hit HTTP 500 on the extension step; its existing profile stays valid if its App ID didn't change
- App Group must be created and assigned to both App IDs in the developer portal: the API can enable `APP_GROUPS` but not create/assign a group (profiles made before that carry an empty group list)
- `ubiquity-kvstore-identifier` needs a stupid-app whose `EntitlementDeriver` substitutes `$(TeamIdentifierPrefix)`/`$(CFBundleIdentifier)` and matches concrete values against trailing-`.*` profile grants; older CLIs fail with "ubiquity-kvstore-identifier value mismatch"
- `stupid-app run --mac` needs this Mac in the development profile

### Build & packaging
- `NoFeedSocialCore` has SwiftPM resources (`.process("Resources")`); stupid-app ≥ 0.0.21 copies them as `NoFeedSocial_NoFeedSocialCore.bundle` (older versions omitted them and `Bundle.module` crashed). Juicebox (static-library XCFramework) needs stupid-app ≥ 0.0.22
- stupid-app's packer sets deployment target 18.0 and the active SDK via linker `-platform_version`; otherwise `LC_BUILD_VERSION` gets `sdk 18.0` and iOS 26 Liquid Glass disappears
- App icon comes from `iconPath` in `stupid-app.yml` (`Resources/AppIcon.appiconset/Icon-1024.png`); the root `Assets.xcassets` doesn't affect packaging
- Background fetch needs only `UIBackgroundModes = fetch` in Info.plist; no custom entitlements file for background modes
- `/.release` (archives, profiles, upload logs) and `__pycache__/` are gitignored

### Install & test
- `stupid-app build` emits the simulator app to `.build/arm64-apple-ios/debug/`; a stale `.build/arm64-apple-ios-simulator/debug/` copy exists and `simctl install` of it silently installs an old binary. Always install with `stupid-app run --simulator`
- Phone not on USB: `stupid-app run --network --udid <udid>`; fails if the iPhone is locked (developer disk image can't mount)
- `xcodebuild test` runs pass `-collect-test-diagnostics never`; otherwise any failure triggers `simctl diagnose --timeout=600` (up to 10 minutes)

### Release & TestFlight
- External TestFlight via ASC API (`scripts/asc_external.py`: groups, get-build, add-to-group, submit): add the build with `POST /v1/builds/{id}/relationships/betaGroups` (`POST /v1/buildBetaGroups` 404s), then `POST /v1/betaAppReviewSubmissions`. `stupid-app release external-beta` does this
- `release external-beta --whats-new` rejects a value starting with `-`; pass `--whats-new=<note>`
- The CLI's external-review poll reads `submissionState`/`state`, but the response exposes `betaReviewState: APPROVED`, so it keeps polling after approval (observed 2026-10-10); verify with `release status --live` or submit with `--no-wait`
- An interrupted release can bump `CFBundleVersion` without archiving/uploading; check App Store Connect's latest build before bumping again
- Before upload, grep the release binary for new endpoint markers to confirm they shipped
